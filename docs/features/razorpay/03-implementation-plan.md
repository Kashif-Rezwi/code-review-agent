## Chunk 5: `PaymentsModule` skeleton

**Goal:** Create the NestJS module with controller, service, repository, DTOs, and credit-cost policy — wired but not yet calling Razorpay. References: audit §4, §5, §7 item 2.

### Files

#### [NEW] `apps/server/src/payments/payments.module.ts`
- **Category:** backend
- **Purpose:** NestJS module registration
- **Responsibility:** Imports `AuthModule`; provides controller, service, repository
- **Dependencies:** `AuthModule`, `PrismaModule` (global)
- **Changes:** Module with `imports: [AuthModule]`, `controllers: [PaymentsController]`, `providers: [PaymentsService, PaymentsRepository]`, `exports: [PaymentsService]`
- **Security:** None — wiring only

#### [NEW] `apps/server/src/payments/payments.controller.ts`
- **Category:** backend
- **Purpose:** HTTP endpoints for `POST /payments/order`, `POST /payments/webhook`, `GET /payments/wallet`
- **Responsibility:** Route handling, auth guard application, delegation to service
- **Dependencies:** `PaymentsService`, `AuthGuard`, `UserThrottlerGuard`
- **Changes:**
  - `@UseGuards(AuthGuard)` at class level (like `ReviewController`)
  - `POST /payments/order` — authenticated, rate-limited (`@UseGuards(UserThrottlerGuard)`, `@Throttle({ default: { limit: 5, ttl: 3_600_000 } })`), accepts `CreateOrderDto`, delegates to `PaymentsService.createOrder(dto.packageId, req.user.userId)`
  - `POST /payments/webhook` — **method-level override**: no `AuthGuard` (decorated with a custom bypass, or placed on a separate controller), signature verification in service, raw body access via `@Req()`
  - `GET /payments/wallet` — authenticated, delegates to `PaymentsService.getWallet(req.user.userId)`
- **Security:**
  - `userId` always from `req.user` — never from request body
  - Webhook route bypasses `AuthGuard` — uses HMAC signature verification instead
  - Order creation rate-limited to 5/hr per user (matches `UserThrottlerGuard` pattern)

> **Design decision — webhook route placement:** NestJS applies `@UseGuards(AuthGuard)` at the class level. The cleanest way to exempt the webhook is to put it on a separate, unguarded controller (`WebhookController`) within the same module — matching the `HealthController` precedent for unguarded routes. This avoids hacky decorator overrides and keeps the intent explicit.

#### [NEW] `apps/server/src/payments/webhook.controller.ts`
- **Category:** backend
- **Purpose:** Dedicated controller for `POST /payments/webhook` — no auth guard
- **Responsibility:** Accepts raw body, delegates to `PaymentsService.handleWebhook()`
- **Dependencies:** `PaymentsService`
- **Changes:** `@Controller('payments')` with a single `@Post('webhook')` route. No `@UseGuards()` at class or method level. Reads `req.rawBody` and `X-Razorpay-Signature` + `X-Razorpay-Event-Id` headers.
- **Security:** Relies entirely on HMAC signature verification in `PaymentsService` — matches the `HealthController` pattern of no auth guard.

#### [NEW] `apps/server/src/payments/payments.service.ts`
- **Category:** backend
- **Purpose:** Business logic for order creation, webhook processing, wallet queries
- **Responsibility:** Razorpay SDK calls, signature verification, credit crediting, free-credit grant
- **Dependencies:** `ConfigService`, `PaymentsRepository`, `razorpay` SDK
- **Changes:**
  - `createOrder(packageId, userId)` — validates packageId against credit-cost policy, calls Razorpay Orders API, creates local `PaymentOrder`
  - `handleWebhook(rawBody, signature, eventId)` — verifies HMAC, deduplicates by eventId, routes to `handleOrderPaid()` or `handlePaymentFailed()`
  - `getWallet(userId)` — returns balance + recent ledger entries + available packages
  - `deductCredits(userId, cost, reviewId, description)` — atomic conditional decrement (architecture §5.1)
  - `refundCredits(userId, cost, reviewId, description)` — compensating transaction for failed reviews
  - `grantFreeCredits(userId)` — idempotent free-credit grant (architecture §6.3)
- **Security:** All Razorpay secrets read via `ConfigService` — never hardcoded. Signature verification uses `crypto.timingSafeEqual`. Credit mutations use atomic `$transaction`.

#### [NEW] `apps/server/src/payments/payments.repository.ts`
- **Category:** backend
- **Purpose:** Prisma queries for payment/credit persistence
- **Responsibility:** DB reads/writes — no business logic, no Razorpay SDK calls
- **Dependencies:** `PrismaService`
- **Changes:**
  - `createOrder(data)` — insert `PaymentOrder` row
  - `findOrderByRazorpayId(razorpayOrderId)` — lookup for webhook processing
  - `captureOrder(razorpayOrderId, razorpayPaymentId, creditsGranted)` — atomic status-guard transition `CREATED → CAPTURED` + credit increment + ledger insert in `$transaction`
  - `failOrder(razorpayOrderId)` — atomic status-guard transition `CREATED → FAILED`
  - `insertEvent(razorpayEventId, razorpayOrderId, eventType, payload)` — idempotency insert (unique constraint catch)
  - `getWallet(userId)` — balance + recent ledger (last 50 entries)
  - `deductCredits(userId, cost, reviewId, description)` — atomic conditional decrement + ledger insert
  - `refundCredits(userId, cost, reviewId, description)` — atomic increment + ledger insert
  - `grantFreeCredits(userId, amount)` — insert `FREE_GRANT` + increment in `$transaction` (unique index guards idempotency)
- **Security:** All `$transaction` blocks use status-guard `where` clauses — the same pattern as `ReviewRepository`.

#### [NEW] `apps/server/src/payments/credit-cost.policy.ts`
- **Category:** backend
- **Purpose:** Server-configurable credit-cost table and credit-package definitions
- **Responsibility:** Pure data — no DB access, no side effects
- **Dependencies:** None
- **Changes:**
  - Export `CREDIT_PACKAGES` — `Record<string, { credits: number, amountPaise: number, currency: string, label: string }>` (architecture §6.1)
  - Export `CREDIT_COSTS` — `Record<string, number>` mapping operation type to credit cost (architecture §6.2): `{ CODE_REVIEW: 5, PR_REVIEW: 10, CHAT: 1 }`
  - Export `FREE_CREDIT_AMOUNT` — `25` (architecture §6.3)
  - Export helper `getCreditCost(type: 'CODE' | 'PR', operation: 'review' | 'chat'): number`
- **Security:** Costs are server-side only — never exposed to the client as modifiable values.

#### [NEW] `apps/server/src/payments/dto/create-order.dto.ts`
- **Category:** backend
- **Purpose:** Input validation for `POST /payments/order`
- **Responsibility:** Class-validator DTO (matches `CreateSessionDto` pattern)
- **Dependencies:** `class-validator`
- **Changes:**
  - `packageId: string` — `@IsString()`, `@IsNotEmpty()`, `@IsIn(Object.keys(CREDIT_PACKAGES))`
- **Security:** `whitelist: true` strips unknown fields. `@IsIn` prevents arbitrary package IDs.

## Chunk 8: Credit guard + consumption

**Goal:** Gate `POST /review/session` and `POST /history/:id/chat` behind a credit-balance check. References: architecture §5.1; audit §6.11, §7 item 4.

### Files

#### [NEW] `apps/server/src/payments/credit.guard.ts`
- **Category:** backend
- **Purpose:** NestJS guard that atomically deducts credits before expensive operations
- **Responsibility:** Check balance, deduct credits, reject if insufficient
- **Dependencies:** `PaymentsService`, `Reflector` (for custom metadata)
- **Changes:**
  - Implements `CanActivate`
  - Reads the credit cost from a custom decorator `@CreditCost(amount)` applied to the route
  - Calls `PaymentsService.deductCredits(userId, cost, null, description)` — if deduction fails (count === 0), throws `HttpException(402, 'Insufficient credits')`
  - Stores the deducted amount on `req` (e.g., `req.creditDeducted = cost`) so that failure-handling code can issue a refund
- **Security:** Atomic conditional decrement — at most one concurrent request wins (architecture §5.1). Guard runs after `AuthGuard` (NestJS guard execution order: class-level first, then method-level).

#### [NEW] `apps/server/src/payments/credit-cost.decorator.ts`
- **Category:** backend
- **Purpose:** Custom decorator `@CreditCost(amount)` to annotate routes with their credit cost
- **Responsibility:** Sets metadata readable by `CreditGuard` via `Reflector`
- **Dependencies:** `@nestjs/common` (`SetMetadata`)
- **Changes:** Single `SetMetadata` call — matches existing NestJS patterns

#### [MODIFY] [`review.controller.ts`](../../../apps/server/src/review/review.controller.ts)
- **Category:** backend
- **Purpose:** Apply credit guard to `POST /review/session`
- **Changes:**
  - Import `CreditGuard` and `CreditCost` decorator
  - Add `@UseGuards(CreditGuard)` and `@CreditCost(CREDIT_COSTS.CODE_REVIEW)` to `createSession()` method (for `type === 'CODE'`)
  - For PR reviews (`type === 'PR'`), the cost is `CREDIT_COSTS.PR_REVIEW`
  - **Design decision:** Since the cost depends on `dto.type` (known only after body parsing), the guard should read `dto.type` from the request body to determine the cost dynamically. Alternative: apply a fixed cost and refund the difference — but this adds complexity. The guard will use `req.body.type` to look up the cost from `CREDIT_COSTS`.
- **Security:** Guard runs after `AuthGuard` and after `ValidationPipe` (body is parsed). If the DTO is invalid, `ValidationPipe` rejects first — no credits deducted.
- **Dependencies:** `PaymentsModule` must be imported by `ReviewModule` (or `CreditGuard` exported globally)

#### [MODIFY] [`history.controller.ts`](../../../apps/server/src/history/history.controller.ts)
- **Category:** backend
- **Purpose:** Apply credit guard to `POST /:id/chat`
- **Changes:**
  - Import `CreditGuard` and `CreditCost` decorator
  - Add `@UseGuards(CreditGuard)` and `@CreditCost(CREDIT_COSTS.CHAT)` to `chat()` method
- **Security:** Same atomic deduction pattern. Chat cost is always 1 credit.

#### [MODIFY] [`review.module.ts`](../../../apps/server/src/review/review.module.ts)
- **Category:** backend
- **Purpose:** Import `PaymentsModule` to make `CreditGuard` available
- **Changes:** Add `PaymentsModule` to `imports` array

#### [MODIFY] `apps/server/src/history/history.module.ts`
- **Category:** backend
- **Purpose:** Import `PaymentsModule` to make `CreditGuard` available
- **Changes:** Add `PaymentsModule` to `imports` array

#### [MODIFY] `apps/server/src/review/review.service.ts`
- **Category:** backend
- **Purpose:** Issue `CONSUMPTION_REFUND` on review failure (architecture §7.4)
- **Changes:** In the existing failure paths (where `markFailed` is called), add a call to `PaymentsService.refundCredits(userId, cost, reviewId, 'Review failed')`. The cost is determined by the review type (`CODE` → 5, `PR` → 10).
- **Security:** Refund only happens when the review transitions to `FAILED` — the same status-guard pattern prevents double-refund.
- **Scope note:** This is a minimal, targeted change — not a refactor of `ReviewService` (safety rail #3, M-10 acknowledged).

### New test files

#### [NEW] `apps/server/src/payments/credit.guard.spec.ts`
- **Category:** test
- **Purpose:** Unit tests for the credit guard
- **Tests:**
  - Sufficient balance → deducts credits, allows request
  - Insufficient balance → returns 402, no review created
  - Concurrent requests race → at most one succeeds (mock-level verification)
  - Missing auth → guard does not run (AuthGuard rejects first)
